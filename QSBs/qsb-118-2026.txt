
             ---===[ Qubes Security Bulletin 118 ]===---

                              2026-08-28

        Dom0 command injection in qvm-copy-to-vm error reporting

User action
------------

Continue to update normally [1] in order to receive the security updates
described in the "Patching" section below. No other user action is
required in response to this QSB.

Summary
--------

A malicious qube can inject arbitrary command to dom0 if user uses
`qvm-copy-to-vm` tool to copy a file from dom0 to such qube.

Impact
-------

An attacker who has control over a qube that is a target of a
user-initiated `qvm-copy-to-vm` call from dom0, can take control over
the whole system.

Issue details 
--------------

The `qvm-copy-to-vm` tool allows copying files out of dom0, to a
selected qube. It uses "qfile" protocol, which is a simplified archive
format including simple file metadata (much simpler than `tar` or
`cpio`). The protocol includes also transfer confirmation at the end,
sent by the target, back to the source. This confirmation includes
checksum of all the transferred files, error code (if any) and name of
the last received file. In case of error, as reported by the error
code field, dom0 displays a GUI message including the error information
and the name of affected file, as reported by the target qube. The
issue exists in the processing of that file name:

1. The `wait_for_result()` function calls `sanitize_remote_filename()`
on received name, before passing it to the error handler:

linux-utils/qrexec-lib/pack.c:

2. Then, `call_error_handler()` calls dom0 variant of the error
reporting function - `gui_fatal()` -> `display_error()`, which uses
`system()` to launch actual error dialog:

core-admin-linux/file-copy-vm/qfile-dom0-agent.c:

     16     char *dialog_cmd;

     29         return;

     31 #undef KDIALOG_CMD
     32 #undef ZENITY_CMD
     33     fprintf(stderr, "%s\n", buf);
     34     system(dialog_cmd);

     37 _Noreturn void gui_fatal(const char *fmt, ...) {
     38     va_list args;

     41     va_end(args);
     42     exit(1);

The issue is that `sanitize_remote_filename()` removes only non-ASCII
characters (and double quotes), but leaves shell meta-characters in.
And then, `system()` runs the constructed command, including
attacker-controlled name via shell.

Note the VM variant of `qvm-copy-to-vm` is not affected, as its
version of the error reporting function does not use `system()`:

Affected systems
-----------------

All Qubes OS versions are affected.

Patching
---------

The following packages contain security updates that address the
vulnerabilities described in this bulletin:

  For Qubes 4.3, in dom0:
  - qubes-core-dom0-linux, version 4.3.22

These packages will migrate from the security-testing repository to the
current (stable) repository over the next two weeks after being tested
by the community. [2] Once available, the packages should be installed
via the Qubes Update tool or its command-line equivalents. [1]
