
             ---===[ Qubes Security Bulletin 124 ]===---

                             2026-11-13

                Partial filtering bypass in Split-gpg2

User action
------------

Continue to update normally via the Qubes Update tool or its
command-line equivalents [1] in order to apply the security updates
described in the "Patching" section below.

Summary
--------

Split-gpg2 filters incoming gpg-agent commands by parsing them, and
then re-constructing allowed commands, possibly removing/replacing
some of its parts. While the input command length is properly
enforced, the command sent to the real gpg-agent after parsing and
re-constructing may be longer than the 1002 characters limit defined by
the GnuPG Assuan protocol. Such too long command sent as a response to
an "INQUIRY" results in gpg-agent ignoring initial 1002 characters and
executing rest of the line as a next command, bypassing split-gpg2
command filtering.

Impact
-------

In the supported configuration, a malicious qube can make gpg-agent
display a password prompt with arbitrary text, and receive response
that user entered. Such prompt will have window borders of the backend
(AKA vault) qube, so it will look like a safe place to enter the
passphrase.
This vulnerability may be used to exploit some further hypothetical
GnuPG issue, that normally would be prevented by the Splig-gpg2
filtering.
In the standard configuration, this issue does not allow extracting or
manipulating secret keys, since Split-gpg2 uses an "extra" gpg-agent
socket that has limited capabilities.

Affected systems
-----------------

All versions of split-gpg2 (split-gpg2 package) are affected.
Split-gpg2 is a different component than Split-gpg (qubes-gpg-split
package)

Note about not security supported configuration
-----------------------------------------------

It is possible to enable `allow_keygen` option in the split-gpg2
config, as documented in the README[5] file:

    ## Allow key generation

    By setting `allow_keygen = yes` in `qubes-split-gpg2.conf` you can allow the client to generate new keys.
    Normal usage should not need this.

    **Warning**: This feature is new and not much tested.
    Therefore it's not security supported!

As noted above, such configuration is not security supported.
When this option is enabled, this vulnerability allows malicious qube
to extract secret keys.

Patching
---------

The following packages contain security updates that address the
vulnerabilities described in this bulletin:

  For Qubes 4.3, in templates used for split-gpg2:
  - split-gpg2 package, version 1.1.16

These packages will migrate from the security-testing repositories to
the current (stable) repositories after being tested by the community.
This testing period is intended to catch bugs affecting Qubes OS
stability before the packages reach the broader userbase. By default,
the security-testing repositories are disabled in both dom0 and
templates. If you wish to receive security updates faster at the risk of
encountering more bugs, you can enable the security-testing repositories
either temporarily (for a single update) or permanently. [2] Dom0,
templates, and standalones each have their own security-testing
repositories, which can be enabled independently of one another. [3][4]
If you do not have the relevant security-testing repositories enabled
while security updates are in security-testing, you must wait until they
migrate to the current (stable) repositories, which generally takes one
to two weeks but may be expedited in urgent cases. Once the packages are
available to your Qubes OS system, you should install them as described
in the "User action" section above.

After you have installed the packages listed above, you must shutdown
relevant templates and restart vault qubes where split-gpg2 is used.
