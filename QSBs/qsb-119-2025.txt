
             ---===[ Qubes Security Bulletin 119 ]===---

                              2026-09-15

    Potentially attacker controlled format string in qvm-open-in-vm

User action
------------

Continue to update normally [1] in order to receive the security updates
described in the "Patching" section below. No other user action is
required in response to this QSB.

Summary
--------

Under certain circumstances (see "Technical details") if the user
invokes qvm-open-in-vm (either directly or through the "Edit in
disposable qube" GUI integration) on a file with an attacker controlled
file name/path the attacker might be able to execute code in the qube in
which the user invoked qvm-open-in-vm.

Impact
-------

If the exploitation is successful the attacker can take control over the
qube in which the user invoked qvm-open-in-vm.

Normally bug that does not cross qube boundary, like this one, is out of
scope for our security support. We make an exception here since it's a
bug in our code and the qvm-open-in-vm functionality is specifically
designed to handle untrusted input. Keep in mind that handling less
trusted input in the same qube is still risks. For example unsafe
handling of attacker controlled paths is an easy error in the shell, or
a file explorer might render a thumbnail of the untrusted input with a
bugy parser, or you you might accidentially open the file with another
application than qvm-open-in-vm exposing the full attack surfare of that
application.

Technical details
------------------

When qvm-open-in-vm is invoked with a file (not an URI) the source side
part of the qrexec call is handled by the qopen-in-vm helper program.
After sending the file content to the other side qopen-in-vm tries to
open a temporary file alongside the original file to save the response
in case the user edited the file in the target qube. If creating this
file fails, for example because the directory is read-only, qopen-in-vm
creates a temporary file in /tmp and shows an error message to the user.
When printing this error message it wrongly invokes the gui_nonfatal
function, such that the original file names ends up in a printf format
string, which is unsafe.

For an attack to be possible multiple conditions need to be fulfilled:

 - The attacker needs to trick the user to open a file with
   qvm-open-in-vm.
  - The file name (last component of the file's path) needs to be longer
    than 248 bytes.
  - Or, the directory that contains the file is not writable.

 - And the path (but not necessarily the last component) needs to
   contain printf-style conversion specifiers (like %n).

 - And qvm-open-in-vm must not have been invoked with the --view-only
   flag.

 - And the target qube either needs to ...
   - send back the file content because it's mtime changed (usually
     because the user saved the file being edited, even if overwriting
     it with the same content),
   - or be compromised by the attacker.

 - The build of qvm-open-in-vm needs to have been compiled without the
   _FORTIFY_SOURCE hardening enabled (or set to a level below 2). Due to
   an unfortunate interaction of our build script with the way Debian
   enables this options, this hardening was not enabled for our Debian
   packages. The Fedora packages had it enabled. With enabled hardening
   the program simply safely aborts with an error, making the bug
   unexploitable.

The first reporter reported exploitability on their system with a low
success probability (< 3 %). Additionally the demo required a very long
path (multiple nested directories) with many format specifiers in it,
making the requirement of the user opening a suspicious looking path
harder.

Affected systems
-----------------

All Qubes OS releases are affected.

From the official templates it's only exploitable in Debian-based
templates.

Patching
---------

The following packages contain security updates that address the
vulnerabilities described in this bulletin:

  For Qubes 4.3, in templates and standalones:
  - qubes-core-agent version 4.3.48

These packages will migrate from the security-testing repository to the
current (stable) repository over the next two weeks after being tested
by the community. [2] Once available, the packages should be installed
via the Qubes Update tool or its command-line equivalents. [1]

All template-based qubes and disposable qubes need must be restarted after
updating and shutting down their template in order for the updates to take
effect.
